# The orchestrator architecture

This page is about *why* the lab is shaped the way it is — why agents write the code and humans only validate, why three markdown files are treated as the single source of truth, and how a DAG executor with parallel waves and checkpoints lets the Owner approve a plan once and then walk away. It is discursive on purpose: it admits the trade-offs that were made and the ones that were deliberately deferred. If you want to *run* the thing, read [How to run the orchestrator](../how-to/run-the-orchestrator.md); if you want the exact flags and env vars, read the [CLI reference](../reference/cli.md) and the [environment reference](../reference/environment.md). This page is the one you can read away from the keyboard.

## The thesis: agents generate, humans validate

The whole lab rests on one division of labour, stated in the very first lines of [the README](../../README.md) and [`CLAUDE.md`](../../CLAUDE.md): *a single Owner drives the app, agents write the code, a human validates.* Every line written by hand is a justified exception, recorded in the commit.

The reason this is a stance and not just a workflow is that it inverts the usual fear about autonomous agents. The fear is "the agent will do something irreversible." The answer here is not "make the agent smarter" — it is "make the irreversible steps the only ones a human touches." Generation is cheap, parallel, and retryable; a bad generation costs an attempt. Validation is where judgement lives, and judgement is exactly the thing we do not want to delegate. So the architecture spends its complexity budget on getting the agent *to* the next human decision safely, and almost none on trying to remove the human decision.

The README states the consequence directly: **between two human decisions, nothing needs a human.** The decision does not disappear — it *moves*. The Owner decides once, when approving the plan, and the run then advances on its own to the next genuine decision (a checkpoint, a block, the merge). That sentence is the design goal that every other mechanism on this page serves.

## The three-artifact contract as source of truth

Before any DAG executes, a unit of work has produced three versioned markdown files in `work/<feature>/`, and `CLAUDE.md` calls them *the source of truth*:

- **`spec.md`** — the WHAT. The business contract: invariants, behaviors, examples, evals. It is the primary prompt for any agent that codes. "Never implement anything absent from the spec."
- **`design.md`** — the HOW. Stack, ADRs, reference repos. Every technical choice must point to a pattern from a reference repo.
- **`tasks.md`** — the DO. The execution plan, generated by the planner agent and approved by the Owner.

The mandatory reading order — spec → design → tasks — is not bureaucratic ceremony; it is the dependency order of *meaning*. The spec constrains the design, the design constrains the plan, and the orchestrator's implementer prompt (`_build_base_prompt` in `lab/engine/orchestrate.py`) literally tells the agent to read all three in that order before executing a single task. The artifacts replace user stories, functional specs, and tickets at once because they are *machine-read*, not just human-read: `parse_tasks_md` in `lab/engine/plan.py` extracts `depends_on`, `files_touched`, `verify`, `implements` from `tasks.md`; plan-lint cross-checks every `implements [INV-2, BHV-3]` against the text of `spec.md`. The contract is enforced because it is parsed.

This is also why the lab is so insistent that *the why lives in git* rather than in a wiki. There is no Confluence, no Jira — "the repo is the memory." A spec amendment is a separate commit with a `version:` bump; an implementation commit carries a `Why:` body and `Spec-IDs` trailers (see the [commit format reference](../reference/commit-format.md)). The reasoning behind a change is recoverable forever via `git log`/`git blame`, which is exactly what the reviewer, planner, and scout agents mine. The broader case for treating the repository as durable memory is its own essay — see [Git as memory](git-as-memory.md). The point here is structural: because the contract and its history are *in the repo the agent already reads*, the agent never needs a human to relay context.

One trade-off worth naming: markdown-as-contract is deliberately *not* a richer format. The lab looked at Google's Open Knowledge Format and chose additive adoption over migration precisely because the orchestration semantics (`depends_on`, `version:` pointers, the build DAG) are things OKF does not model — see [the OKF evaluation](okf-evaluation.md). Plain markdown plus a parser beats a heavier schema because the parser is small enough to trust and the files stay diffable.

## The DAG, the waves, and the checkpoints

The executor lives in `lab/engine/orchestrate.py` and its `main()` loop is small enough to hold in your head. `tasks.md` parses into a list of `Node`s (`lab/engine/plan.py`), each with a `depends_on` edge set. That makes the plan a directed acyclic graph — plan-lint refuses a cyclic one — and the loop repeatedly computes the *ready frontier*: every pending node whose dependencies are all `done`. This is the heart of "nothing needs a human between two decisions": the loop never asks where to go next, it computes it from the graph.

Within a frontier, the executor separates *tasks* from *checkpoints*. Tasks with no remaining dependency on each other run in a **parallel wave** through a `ThreadPoolExecutor(max_workers=MAX_PARALLEL)` (`MAX_PARALLEL = 3`). Checkpoints are handled afterward, one at a time, by `wait_checkpoint`. The shape of the run is therefore: a wave of parallel implementers, then a checkpoint, then the next wave the checkpoint unlocked. The README distils the parallelism into three principles, and they are worth reading as design philosophy rather than mechanics:

1. **Parallelize the research, never the decision.** `design-scout` explores internal repos and OSS references concurrently; writing and validating the design is sequential. Fan-out is for gathering; convergence is for deciding.
2. **Parallelize tasks with no file dependency.** Two tasks may run together only if their `files_touched` are disjoint *and* neither depends on the other — otherwise strict sequence. This is enforced statically by plan-lint, which flags two unordered tasks whose paths overlap (`paths_overlap` in `lab/engine/plan.py`), so a file collision is caught *before* the run rather than discovered as a corrupted commit during one.
3. **Every point of no return is a human checkpoint.** Plan generation, merge, deploy: the agent proposes, the human disposes.

Checkpoints come in two modes (`mode: blocking` default, `mode: auto`). A `blocking` checkpoint pauses and notifies; the Owner runs `lab/engine/approve.sh` or `lab/engine/reject.sh`. An `auto` checkpoint is auto-validated *if and only if* the evals are green **and** the reviewer panel returns `PASS` — and on any doubt it falls back to blocking. Two safeguards keep `auto` honest: the final (merge) checkpoint is *always* blocking (plan-lint rejects an `auto` checkpoint that is a sink or whose title mentions "merge"), and a model is never allowed to wave through its own work — if the only available reviewer model is the implementer's model, separation of duties is impossible and the checkpoint falls back to human (`run_review` returns `self_review_only`). The autonomy levels in the README (`--dry-run`, `--supervised`, default cruise) are just policies over this same machinery: `--supervised` forces every checkpoint to blocking, cruise respects the modes the Owner approved.

Failure does not abort the run. If a task fails or blocks, `skip_dependents` neutralizes only its transitive subtree (those nodes become `skipped`); sibling branches keep running, and the loop always ends on a printed summary. This **failure containment** is what makes background, unattended runs tolerable — one bad task does not waste a whole wave's worth of others.

## Why the guardrails exist

Autonomy is only safe if the agent cannot quietly do the wrong thing while no human is watching. Each guardrail closes a specific way an unsupervised agent could *appear* to succeed while actually doing nothing, or doing something out of scope. They are best understood as answers to "how would a misaligned-but-not-yet-malicious agent game this?"

**Anti-empty-gate.** The eval gate is binary: no green eval, no merge. But "green" is trivially gameable — `just evals` exits 0 when there are *zero* evals to run. So `_eval_gate` collects the evals (`pytest -m eval --collect-only`) and *fails* a task that implements spec IDs, or merely touches source code, while collecting no eval at all. It goes further: each declared `EVAL-n` must be carried by a test whose pytest node-id contains the lowercased ID (`eval_covers`), so `eval_1` cannot satisfy `EVAL-10` and a file path does not count as coverage. The gate is mechanically un-bluffable. This pairs with the **structured verdict**: an implementer must end with `STATUS: done` or `STATUS: blocked — <reason>`. An agent that hits a spec gap records an open question and ends *blocked* — it never launders an unanswered question into a "done."

**Scoped commits.** When a wave of three implementers runs in parallel, naive `git add -A` would let each agent's commit absorb the others' files — and, worse, sweep the `evals/golden/` oracles into a task commit, corrupting the ground truth the scorecard is judged against. So `scoped_commit` stages only the task's `files_touched` plus the feature directory, under a `COMMIT_LOCK`, and explicitly un-stages any golden that is not declared in `files_touched`. Out-of-scope changes are *reported, not committed*. The commit message uses the same canonical shape as the human `/commit` skill (`_commit_message`), so the orchestrator's `[auto]` history reads uniformly with the human history — which is the whole premise of git-as-memory.

**Signed approvals.** A checkpoint approval is a file in `.approvals/<CP>`. Since an agent with Bash or edit tools could write that file itself, the gate cannot reduce to "does the file exist." Approvals are HMAC-signed (`lab/engine/approvals.py`), verified before being honored, and consumed afterward so a token never replays. The orchestrator is *fail-closed*: a plan with checkpoints refuses to start unless `LAB_APPROVAL_SECRET` is set (the explicit opt-out is `LAB_ALLOW_UNSIGNED_APPROVALS=1`). The secret is stripped from every sub-agent's environment (`run_claude` filters `approvals.ENV_SECRET`), and `.approvals/`/`.runs/` are denied to the agent's edit tools.

**The verify boundary.** A task's `verify` materializes its `done_when` as an executable check, run after the agent and before the evals. It is *never* a shell. `parse_verify` (`lab/engine/verify.py`) splits it into an argv list, rejects shell metacharacters, restricts the command to an allowlist and any env prefix to a small allowlist (so `PYTHONPATH=src uv run …` is fine but `LD_PRELOAD=…` is an RCE escalation and is refused). When the Owner approves the plan they implicitly sign these commands — plan-lint surfaces every `verify` so they can be read first.

**Concurrency and crash safety.** Two orchestrators on one feature would race on `state.json`, the git index, the journal, and the per-process budget counter, so `acquire_orchestrator_lock` takes an exclusive OS `flock` on `.runs/orchestrator.lock` and fails the second run fast. `state.json` is written atomically (tempfile + `os.replace`) so a kill mid-write cannot truncate it, and resume tolerates an unreadable state by restarting clean rather than crashing. These are not glamorous, but they are what make "run it in the background overnight" a sentence you can say without fear.

A useful way to read these guardrails together: each one removes a way the run could *silently* drift from the contract while the Owner is away. That is the price of "between two decisions, nothing needs a human" — you only get to leave if leaving is provably safe.

## The module split, and why it is shaped this way

`orchestrate.py` is the engine — the loop, the waves, the gates, the checkpoints — and it deliberately delegates everything that can be made *pure* or *swappable* to sibling modules:

- **`plan.py`** — the `Node` model, `parse_tasks_md`, and DAG helpers (`ancestors`, `paths_overlap`, `skip_dependents`). Pure, no orchestrator state. Shared by the engine *and* plan-lint, so the executor and the linter cannot disagree about what the plan means.
- **`planlint.py`** — static validation: acyclic graph, spec IDs that exist, `done_when` present, disjoint parallel paths, final checkpoint blocking, every `verify` on the allowlist. It is pure (parsed nodes + registry → errors/warnings) and is what lets the Owner approve once and walk away. A plan that does not lint does not run.
- **`verify.py`** — the no-shell verify policy, isolated so the same rule is enforced identically by the engine and the linter and is testable on its own.
- **`notify.py`** — terminal banner, optional macOS notification, optional team chat webhook, all best-effort and silenced in CI. Pure side-effect, no state.
- **`journal_io.py` / `run_report.py` / `trajectory_guard.py` / `context_budget.py`** — the read-only inspection layer over the run telemetry: the shared `.runs/journal.jsonl` reader, the cross-feature report (first-pass rate, cost per role/model), the trajectory checks (journal integrity, commit scope), and the static-context measurement. None of them mutate anything; they observe what the engine recorded.
- **`runner.py` / `sandbox_runner.py`** — the execution backend (below).

This is the classic move of pushing decisions and side-effects to the edges so the core stays a thin policy loop. The payoff is testability: the README notes that `tests/orchestrator/` replays the whole mechanism — lint, waves, containment, resume, auto checkpoints, anti-empty-gate, signed approvals — in seconds against a deterministic `claude` shim. That is only possible because the engine talks to interfaces (`AgentRunner`) and pure functions, not to a binary.

## The runner abstraction and the trust model

The single most important seam is `AgentRunner` in `runner.py`. The orchestrator never calls the `claude` binary directly; it calls `RUNNER.run(...)`. That one indirection is what lets the *execution backend* change without touching orchestration logic, and it is also where the lab's honesty about its own threat model lives.

There are two implementations today, selected by `LAB_RUNNER`:

- **`claude-cli`** (default) runs the agent on the *host*, confined only by tool allowlists (`--allowedTools`, the `verify` allowlist, the `settings.json` denies). An implementer that runs its own tests has code execution, so on the host the signed-approval boundary is *defense-in-depth that raises the bar*, not a hard wall — a determined, code-executing agent could in principle read the Owner's dotfiles and exfiltrate the secret.
- **`sandbox`** (`LAB_RUNNER=sandbox`, see [Use the sandbox](../how-to/use-the-sandbox.md)) runs the *same* `claude -p` call — `claude_argv` is shared, so the agent-facing command is byte-identical — inside a hardened container: only the repo is mounted, the approval secret is never forwarded in (`curate_env` asserts its absence), egress is allowlisted, and the process is non-root with a read-only rootfs and dropped capabilities. Making the secret *unreachable* is what turns the approval crypto into a *real* boundary.

The README states the intended threat model plainly: a **trusted-but-possibly-misaligned** agent under the host runner; a **malicious** agent under the sandbox runner. Naming both, rather than pretending the host runner is airtight, is itself a design choice — it tells the operator exactly which boundary they are relying on. And because the seam is an abstract interface, a future cross-vendor runner (Vertex / Gemini) is "just another `AgentRunner`," which the [backlog](../../README.md) acknowledges as a drop-in rather than a rewrite.

## Alternatives and trade-offs

A few choices here were genuinely contested and are worth recording as choices, not facts of nature.

- **Forbid file collisions vs make them impossible.** Today, parallel tasks with overlapping `files_touched` are *forbidden* by plan-lint. A stronger design — a git worktree per parallel task — would make collisions *impossible*. The lab deliberately deferred it (it is in the backlog) to avoid destabilizing a verified orchestrator; "forbidden and checked" was judged good enough to ship, "impossible by construction" deserves its own PR. This is the recurring posture: prefer the smaller mechanism that is provably correct now over the larger one that is correct in theory.
- **Auto checkpoints vs always-human.** Allowing `mode: auto` reintroduces some risk of an automatic decision. The mitigation is layered (evals green *and* panel PASS *and* separation of duties *and* never on the merge), and the choice of `auto` belongs to the Owner *at approval time*, not to the agent. The alternative — every checkpoint human — is `--supervised`, one flag away. Autonomy here is a dial the Owner sets, not a property baked into the engine.
- **Host runner as default.** Defaulting to the less-confined runner is a usability choice, paid for honestly by the explicit trust-model statement and the fail-closed secret check. The sandbox exists for when the threat model is "malicious"; for "misaligned" the host runner plus guardrails is the pragmatic default.

The thread connecting all of these is the opening thesis. Generation is delegated and parallel because it is cheap and reversible; validation is reserved for humans because it is where irreversibility and judgement meet. Everything between — the DAG, the waves, the gates, the locks, the runner seam — exists so that the stretch between two human decisions can be crossed with no human in it, and crossed *safely*.
